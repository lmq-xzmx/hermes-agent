# 需求依赖矩阵（Requirements Dependency Matrix）方法论

> **版本**: 1.1
> **更新日期**: 2026-05-02
> **目的**: 建立需求间矛盾、重叠、依赖关系的管理方法
> **适用范围**: 需求变更管理、矛盾协调、RTM 补充

---

## 一、核心概念

### 1.1 什么是需求依赖矩阵（RDM）

需求依赖矩阵（Requirements Dependency Matrix，简称 RDM）是一种用于识别和管理需求之间关系的工具。它通过在行和列中列出所有需求，在交叉单元格中标识两个需求之间的关系类型。

```
需求依赖矩阵示意图:

           REQ-1   REQ-2   REQ-3   REQ-4
        ┌────────┬────────┬────────┬────────┐
REQ-1   │   -    │ 矛盾   │  重叠  │  独立  │
        ├────────┼────────┼────────┼────────┤
REQ-2   │  矛盾  │   -    │  依赖  │  独立  │
        ├────────┼────────┼────────┼────────┤
REQ-3   │  重叠  │  依赖  │   -    │  前置  │
        ├────────┼────────┼────────┼────────┤
REQ-4   │  独立  │  独立  │  前置  │   -    │
        └────────┴────────┴────────┴────────┘
```

### 1.2 RDM 与 RTM 的区别

| 维度 | RTM (需求跟踪矩阵) | RDM (需求依赖矩阵) |
|------|---------------------|-------------------|
| **核心功能** | 追踪需求 → 实现 → 验证 | 识别需求间关系 |
| **关注点** | 纵向追溯 (前向/后向) | 横向关系 (矛盾/依赖) |
| **解决问题** | 需求是否实现 | 需求是否冲突 |
| **使用场景** | 需求全生命周期 | 变更影响分析 |
| **关系类型** | 实现/验证映射 | 矛盾/重叠/依赖/独立 |

### 1.3 关系类型定义

| 关系类型 | 符号 | 定义 | 处理策略 |
|---------|------|------|---------|
| **矛盾** | 🔴 | 两个需求相互冲突，无法同时满足 | 优先级排序，保留高优先 |
| **重叠** | 🟡 | 两个需求有重复内容 | 合并或划清边界 |
| **依赖** | 🔵 | 一个需求的实现依赖另一个 | 确保被依赖项先完成 |
| **前置** | 🟢 | 一个需求必须先于另一个完成 | 调整执行顺序 |
| **独立** | ⚪ | 两个需求无直接关系 | 无需特殊处理 |

## 二、矛盾项管理流程

### 2.1 矛盾类型分类

| 矛盾类型 | 描述 | 示例 |
|---------|------|------|
| **逻辑冲突** | 需求内容在逻辑上相互否定 | "必须显示所有文件" vs "隐藏已删除文件" |
| **资源冲突** | 共享资源无法同时满足两个需求 | 存储配额分配给 A 则 B 减少 |
| **时间冲突** | 执行时间或截止时间相互冲突 | 功能 X 必须在 Y 之前完成 vs Y 必须在 X 之前完成 |
| **权限冲突** | 权限设置相互矛盾 | 用户可删除自己文件 vs 用户不可删除任何文件 |
| **边界冲突** | 数值边界设置相互矛盾 | 配额上限 100GB vs 单文件最大 200GB |

### 2.2 矛盾处理四步法

```
┌─────────────────────────────────────────────────────────────────┐
│                    矛盾处理四步法                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Step 1: 记录矛盾                                               │
│  ─────────────────                                              │
│  • 明确两个矛盾需求的编号和内容                                  │
│  • 标注矛盾性质（逻辑/资源/时间/权限/边界）                      │
│  • 保留矛盾记录，不可简单删除                                    │
│                                                                 │
│  Step 2: 协调讨论                                               │
│  ─────────────────                                              │
│  • 组织利益相关者会议                                           │
│  • 解释矛盾根本原因和潜在影响                                   │
│  • 获取决策方明确意见                                           │
│                                                                 │
│  Step 3: 置信度评估与处理                                       │
│  ──────────────────────────────────────────────────────────── │
│  • AI 提供处理建议                                              │
│  • 结合代码状态、文档逻辑、项目目标评估置信度                  │
│  • 置信度 ≥ 80%：按建议处理，记录到 RDM                       │
│  • 置信度 < 80%：提交用户选择，记录到 RDM                     │
│                                                                 │
│  Step 4: 更新记录                                               │
│  ─────────────────                                              │
│  • 将修改后需求更新到 RTM/RDM                                   │
│  • 在备注中记录矛盾处理过程和决策依据（含置信度）               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 置信度评估与处理

```
┌─────────────────────────────────────────────────────────────────┐
│                    置信度评估机制                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  评估维度 (置信度总分 100%)                                    │
│  ──────────────────────────────────────────────────────────── │
│                                                                 │
│  ① 代码实际状态核实                    权重: 30%                │
│     • 是否已实现相关代码？                                     │
│     • 代码与文档描述是否一致？                                 │
│     • 是否存在已有实现可复用？                                 │
│                                                                 │
│  ② 文档逻辑一致性                     权重: 25%                │
│     • RTM/RDM/设计文档是否一致？                              │
│     • 需求描述是否有明确定义？                                 │
│     • 优先级标注是否清晰？                                     │
│                                                                 │
│  ③ 项目目标符合度                     权重: 25%                │
│     • 是否符合 v2.0 升级目标？                                 │
│     • 是否符合 SMART 原则？                                    │
│     • 是否在当前 Sprint 范围内？                               │
│                                                                 │
│  ④ 历史类似案例参考                   权重: 20%                │
│     • 是否有类似矛盾处理先例？                                 │
│     • 先例处理结果是否持续有效？                               │
│                                                                 │
│  置信度判定                                                   │
│  ──────────────────────────────────────────────────────────── │
│  • ≥ 80%: **AI 自动采纳建议，直接处理，记录到 RDM**          │
│  • 60-79%: AI 提供建议，提交用户最终选择                    │
│  • < 60%: 显著标记，提交用户决策                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3.1 置信度低于80%的处理规则

当置信度低于80%时，必须遵循以下转化和处理规则：

| 情况 | 处理方式 | 标注格式 |
|------|---------|---------|
| **数据库/部署状态问题** | 标记为"部分实现"，备注"待部署验证" | `⚠️ 部分实现，备注'待部署验证'` |
| **业务概念边界不明确** | 先参考行业最佳实践，无法确认时提交用户决策 | 参考最佳实践后提交用户 |
| **测试基础设施问题** | 遵循 TDD 红绿测试标准，参考测试金字塔 | 参考 TDD 标准 |
| **任务编号需转化** | 将任务编号转化为实际需求（REQ-M*-* 格式） | 使用 REQ-M*-* 格式 |

**用户语言转化要求**：
```
转化原则：
1. 技术分析 → 用户可理解的语言
2. 提供代码事实（文件路径、行号）
3. 提供设计意图说明
4. 明确标注模糊区域（⚠️ 待确认）
5. 所有需求引用使用 REQ-M*-* 格式
```

**数据库/部署问题处理示例**：
```
问题：REQ-M2-017 配额超卖防护状态不一致
分析：
  - 代码位置：lifecycle_engine.py:156
  - 实现状态：⚠️ 部分实现（无 SELECT FOR UPDATE）
  - 部署状态：待生产环境验证
处理：
  → 标记为 ⚠️ 部分实现，备注'待部署验证'
  → 提交用户确认：是否需要当前环境部署验证？
```

**业务概念最佳实践参考顺序**：
```
1. 查找行业标准（如 RFC、ISO 标准）
2. 参考主流云服务厂商做法（如 AWS S3、GCP Storage）
3. 引用项目内部最佳实践文档
4. 若仍无法确认 → 提交用户决策
```

**TDD 红绿测试参考标准**：
```
测试基础设施评估标准：
├── Red（红）：写一个失败测试，明确期望行为
├── Green（绿）：写最简单代码让测试通过
├── Refactor（重构）：优化代码，保持测试通过
└── 参考测试金字塔：单元测试 → 集成测试 → E2E 测试
```

### 2.3.1 置信度评估示例

| 场景 | 评估维度得分 | 总分 | 决策 |
|------|-------------|------|------|
| **场景A**: REQ-M3-001 与 REQ-M3-002 重叠 | ①30 + ②25 + ③25 + ④20 = **100%** | ✅ 100% ≥ 80% | AI 自动采纳 |
| **场景B**: REQ-M2-017 配额超卖 vs M1-002 配额显示 | ①15 + ②15 + ③20 + ④10 = **60%** | ⚠️ 60% < 80% | 提交用户选择 |
| **场景C**: 新需求 vs 已有架构设计冲突 | ①10 + ②20 + ③15 + ④5 = **50%** | 🔴 50% < 60% | 显著标记，用户决策 |

### 2.4 矛盾决策矩阵

当两个需求矛盾时，使用以下决策矩阵：

| 决策因素 | 权重 | 说明 |
|---------|------|------|
| **业务价值** | 30% | 哪个需求带来更大业务价值 |
| **紧急程度** | 25% | 哪个需求更紧急 |
| **实现成本** | 20% | 哪个需求成本更低 |
| **用户影响** | 15% | 哪个需求影响更多用户 |
| **技术风险** | 10% | 哪个需求风险更低 |

**决策结果**:
- 得分高者 → 保留为正式需求
- 得分低者 → 降级为"可选"或移入"待定"池

### 2.5 历史记录保留原则（标准实施指导思想）

> **核心原则**: 矛盾记录永不删除，只标记状态

```
┌─────────────────────────────────────────────────────────────────┐
│                    历史记录保留原则                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 矛盾记录永不删除                                            │
│     • 即使已解决，矛盾记录也永久保留                            │
│     • 便于后续审计和复盘                                        │
│                                                                 │
│  2. 状态流转                                                    │
│     [待处理] → [处理中] → [已解决] 或 [已推迟]               │
│                                                                 │
│  3. 保留目的                                                    │
│     • 防止错误决策被遗忘                                       │
│     • 支持后续 Review 和复盘                                    │
│     • 积累决策经验供未来参考                                    │
│     • 追溯"为什么这样决定"的依据                               │
│                                                                 │
│  4. Review 时机                                                │
│     • 每月定期审查历史矛盾                                      │
│     • 验证决策是否持续正确                                      │
│     • 发现决策错误时及时修正                                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**执行要点**:
| 要点 | 说明 |
|------|------|
| 永不删除 | 所有矛盾记录永久保留在矛盾登记册 |
| 状态标记 | 通过状态字段区分"待处理/处理中/已解决/已推迟" |
| 决策追溯 | 记录决策依据，支持后续理解"为什么这样决定" |
| 定期 Review | 每月审查历史矛盾，验证决策是否持续正确 |

## 三、重叠项管理

### 3.1 重叠类型

| 重叠类型 | 描述 | 处理方式 |
|---------|------|---------|
| **完全重叠** | 两个需求描述完全相同 | 合并为一个，删除重复 |
| **包含重叠** | 一个需求完全包含另一个 | 保留完整者，删除被包含者 |
| **交叉重叠** | 两个需求部分重叠 | 划清边界，明确各自范围 |

### 3.2 重叠处理流程

```
发现重叠
    │
    ├── 完全重叠? ──→ 合并为一个需求
    │
    ├── 包含重叠? ──→ 保留完整需求
    │
    └── 交叉重叠? ──→ 明确边界
                          │
                          ├── 范围A vs 范围B
                          └── 更新需求描述
```

## 四、依赖项管理

### 4.1 依赖类型

| 依赖类型 | 符号 | 描述 | 示例 |
|---------|------|------|------|
| **必需依赖** | 🔵🔵 | 必须同时实现 | A 必须使用 B 提供的接口 |
| **可选依赖** | 🔵⚪ | 可选搭配 | 缓存功能依赖缓存服务但非必需 |
| **反向依赖** | 🔵← | A 依赖 B，B 也依赖 A | 需要接口重构 |
| **自依赖** | 🔵↑ | 需求依赖自身 | 需要拆分 |

### 4.2 依赖关系图

```
必需依赖示例:

REQ-M2-017 (配额超卖防护)
    │
    ├── 依赖 → REQ-M2-001 (配额超限拦截)
    │
    └── 依赖 → REQ-M1-002 (AdminOverview 配额显示)

执行顺序:
1. REQ-M2-001 (先实现基础配额检查)
2. REQ-M2-017 (再实现 SELECT FOR UPDATE)
3. REQ-M1-002 (最后更新配额显示)
```

## 五、RDM 与 RTM 的协同

### 5.1 协同关系

```
┌─────────────────────────────────────────────────────────────────┐
│                    RTM + RDM 协同模型                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│    RTM (纵向追踪)                    RDM (横向关系)              │
│    ───────────────                  ──────────────              │
│    需求 → 设计 → 编码               矛盾识别                    │
│    → 测试 → 验证                    重叠合并                    │
│                                      依赖排序                    │
│                                                                 │
│         ↓                                  ↓                    │
│    ┌─────────────────────────────────────────┐                 │
│    │         项目需求全生命周期管理            │                 │
│    │   (RTM 确保实现，RDM 确保无冲突)        │                 │
│    └─────────────────────────────────────────┘                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 协同工作流

```
┌─────────────────────────────────────────────────────────────────┐
│                    需求管理工作流                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 需求收集                                                    │
│     ↓                                                           │
│  2. RTM 登记 (需求 ID、描述、状态)                             │
│     ↓                                                           │
│  3. RDM 分析 (矛盾/重叠/依赖)                                   │
│     ↓                                                           │
│     ├── 发现矛盾? ──→ 矛盾处理流程 ──→ 返回 Step 2            │
│     │                                                            │
│     ├── 发现重叠? ──→ 重叠合并 ──→ 返回 Step 2                │
│     │                                                            │
│     └── 无冲突 ──→ 继续                                         │
│     ↓                                                           │
│  4. 开发执行                                                    │
│     ↓                                                           │
│  5. RTM 验证                                                    │
│     ↓                                                           │
│  6. 需求变更? ──→ 返回 Step 2                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 六、配套管理机制

### 6.1 变更控制委员会（CCB）

| 角色 | 职责 |
|------|------|
| 决策者 | 矛盾处理最终决策 |
| 业务代表 | 业务优先级判断 |
| 技术代表 | 技术可行性和成本评估 |
| QA 代表 | 质量影响评估 |

**CCB 会议频率**: 每周一次，紧急问题可临时召集

### 6.2 需求优先级（MOSCOW）

| 优先级 | 定义 | 处理方式 |
|--------|------|---------|
| **Must-have** | 必须实现，否则系统不可用 | 矛盾时优先保留 |
| **Should-have** | 重要但非必需 | 矛盾时次优先 |
| **Could-have** | 期望但可推迟 | 矛盾时可降级 |
| **Won't-have** | 明确不包含 | 矛盾时优先移除 |
