> **版本**: 1.2
> **更新日期**: 2026-05-05
> **目的**: 建立需求间矛盾、重叠、依赖关系的管理方法
> **适用范围**: 需求变更管理、矛盾协调、RTM 补充
---

## 一、管理职责

### 1.1 角色定义

| 角色 | 职责 | 人员 |

| RDM 管理员 | 维护 RDM 矩阵，协调矛盾处理 | 技术负责人 |

### 1.2 维护频率

| 活动 | 频率 | 负责人 |

| RDM 与 RTM 同步 | 每 Sprint | RDM 管理员 |

## 二、日常管理操作

### 2.1 新增需求

**操作步骤**:
1. 在 `RDM_Requirements_Dependency_Matrix.md` 中添加需求行/列
2. 与现有需求逐一对比，填写关系类型
3. 如发现矛盾，立即登记到矛盾登记册
4. 更新 RTM.md 中的需求注册表
5. 通知相关需求负责人

**新增需求检查清单**:
```
新增需求 REQ-XXX:
├── [ ] 已添加到 RDM 矩阵
├── [ ] 已与所有现有需求对比关系
├── [ ] 如有矛盾，已登记到矛盾登记册
├── [ ] 如有依赖，已通知被依赖需求负责人
├── [ ] RTM.md 已同步更新
└── [ ] 通知相关干系人
```

### 2.2 需求变更

**操作步骤**:
1. 确认变更范围，识别受影响需求
2. 检查变更是否引入新矛盾
3. 更新 RDM 矩阵中相关关系
4. 如有矛盾，按矛盾处理流程执行
5. 更新 RTM.md 变更记录
6. 通知受影响的需求负责人

**变更影响查询**:
```bash
# 查询某个需求的影响范围
grep "REQ-M2-017" RDM_Requirements_Dependency_Matrix.md
grep "REQ-M2-017" RTM.md
```

### 2.3 矛盾处理

**触发条件**: 发现新的矛盾需求

**处理流程**:
```
发现矛盾
    │
    ↓
Step 1: 记录矛盾 (CONF-ID 生成)
    │
    ├── 填写矛盾描述
    ├── 分析矛盾类型
    └── 初步影响评估
    │
    ↓
Step 2: 矛盾协调会议
    │
    ├── 召集 CCB 委员
    ├── 讨论矛盾根因
    └── 评估各方案利弊
    │
    ↓
Step 3: 决策与执行
    │
    ├── CCB 投票决策
    ├── 更新 RDM 矩阵
    └── 更新 RTM 需求
    │
    ↓
Step 4: 通知与归档
    │
    ├── 通知受影响干系人
    └── 归档矛盾处理记录
```

## 三、矛盾处理记录

### 3.0 历史记录保留原则

> **核心原则**: 矛盾记录永不删除，只标记状态

```
┌─────────────────────────────────────────────────────────────────┐
│                    历史记录保留原则                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 矛盾记录永不删除                                            │
│     • 即使已解决，矛盾记录也永久保留                            │
│     • 便于后续审计和复盘                                        │
│                                                                 │
│  2. 状态流转                                                   │
│     [待处理] → [处理中] → [已解决] 或 [已推迟]               │
│                                                                 │
│  3. 保留目的                                                   │
│     • 防止错误决策被遗忘                                       │
│     • 支持后续 Review 和复盘                                    │
│     • 积累决策经验供未来参考                                    │
│     • 追溯"为什么这样决定"的依据                               │
│                                                                 │
│  4. Review 时机                                               │
│     • 每月定期审查历史矛盾                                      │
│     • 验证决策是否持续正确                                      │
│     • 发现决策错误时及时修正                                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.2.1 置信度低于80%的处理规则

当矛盾置信度低于80%时，必须遵循以下规则进行用户语言转化和确认：

| 情况 | 处理方式 | 标注格式 |
|------|---------|---------|
| **数据库/部署状态问题** | 标记为"部分实现"，备注"待部署验证" | `⚠️ 部分实现，备注'待部署验证'` |
| **业务概念边界不明确** | 先参考行业最佳实践，无法确认时提交用户决策 | 参考最佳实践后提交用户 |
| **测试基础设施问题** | 遵循 TDD 红绿测试标准，参考测试金字塔 | 参考 TDD 标准 |
| **任务编号需转化** | 将任务编号转化为实际需求（REQ-M*-* 格式） | 使用 REQ-M*-* 格式 |

**转化检查清单**：
```
转化前准备：
├── [ ] 技术分析已转化为用户可理解语言
├── [ ] 代码事实已标注（文件路径、行号）
├── [ ] 设计意图已说明
├── [ ] 模糊区域已明确标注 ⚠️
└── [ ] 所有需求引用使用 REQ-M*-* 格式

情况判定：
├── [ ] 数据库/部署问题？ → 标注 ⚠️ 部分实现，备注'待部署验证'
├── [ ] 业务概念边界？ → 参考最佳实践 → 提交用户
├── [ ] 测试基础设施？ → 参考 TDD 红绿测试标准
└── [ ] 任务编号？ → 转化为 REQ-M*-* 格式
```

**最佳实践参考优先级**：
```
1. 行业标准（RFC、ISO、W3C 等）
2. 主流云厂商实践（AWS、GCP、Azure）
3. 项目内部最佳实践文档
4. 若仍无法确认 → 提交用户决策
```

**TDD 红绿测试参考标准**：
```
测试基础设施评估：
├── Red（红）：写一个失败测试，明确期望行为
├── Green（绿）：写最简单代码让测试通过
├── Refactor（重构）：优化代码，保持测试通过
└── 测试金字塔：单元测试 → 集成测试 → E2E 测试
```

## 四、RDM 与 RTM 同步机制

### 4.1 同步规则

| 触发事件 | RDM 更新 | RTM 更新 |
|---------|---------|---------|
| 新增需求 | 添加到矩阵 | 添加到需求注册表 |
| 需求状态变更 | - | 更新"状态"字段 |
| 发现矛盾 | 登记到矛盾册 | - |
| 矛盾处理完成 | 更新矛盾状态 | 更新需求"备注" |
| 需求合并 | 更新矩阵关系 | 更新需求描述 |
| 需求删除 | 删除矩阵行/列 | 标记"已删除" |

### 4.2 同步检查清单

```

├── [ ] 矛盾登记册与 RTM 备注已同步
├── [ ] 依赖关系与 RTM 中的"关联设计文档"一致
```
