## 二、能通过 SSO/RBAC 打通的部分

### 2.1 ✅ 可以打通的

| 路径 | 说明 |
|------|------|
| **File Manager → LLM Wiki** | File Manager 的 JWT 验证传入 team_id + user_id，LLM Wiki 按团队隔离 wiki 存储 |
| **Claudian MCP → File Manager** | 通过 MCP 调用 File Manager API，JWT 验证，RBAC 权限生效 |
| **Claude Code → File Manager** | 同上，通过 MCP 或 API |
| **Web UI → File Manager → LLM Wiki** | 用户在 File Manager Web 中触发知识同步，权限跟随账号 |
| **hermes-mcp → File Manager** | STDIO 模式 MCP Server，JWT Token 随请求传入，RBAC 权限生效 |
| **hermes-mcp → LLM Wiki** | 通过 File Manager 代理访问，team_id 隔离编译产物 |

### 2.2 SSO 打通实现细节：Hermes File Manager ↔ LLM Wiki

#### JWT Token 结构

File Manager 的 Auth Service 签发统一 JWT，LLM Wiki 验证后获取用户上下文：

```json
{
  "sub": "user_uuid",
  "username": "alice",
  "email": "alice@example.com",
  "teams": ["team_hermes", "team_research"],
  "roles": {"team_hermes": "admin", "team_research": "viewer"},
  "exp": 1700000000,
  "iat": 1699996400,
  "type": "access",
  "jti": "token_uuid"
}
```

#### LLM Wiki 认证中间件

```python
class HermesAuthMiddleware:
    """从 Hermes File Manager 传递的 JWT 验证"""

    def verify_token(self, token: str) -> UserContext:
        try:
            payload = jwt.decode(
                token,
                JWT_SECRET,
                algorithms=["HS256"]
            )
            return UserContext(
                user_id=payload["sub"],
                username=payload["username"],
                teams=payload.get("teams", []),
                roles=payload.get("roles", {}),
            )
        except jwt.ExpiredSignatureError:
            raise AuthError("Token 已过期，请重新登录")
```

```

│                    SSO 用户权限状态流转                            │
├─────────────────────────────────────────────────────────────────┤
```

**SSO 用户首次登录时的权限状态**：
- 默认状态：`limited_access`（可登录，无法访问任何 Team/Space）
- 触发权限获取：Admin 分配 或 自动同步组织架构

### 2.3 ⚠️ 部分可以打通

| 路径 | 说明 |
|------|------|
| **OpenHuman → File Manager** | OpenHuman 的 auto-fetch 数据可以通过 MCP/API 写入 File Manager 空间（需 OpenHuman 支持 MCP 客户端模式） |
| **Hermes 主系统 → File Manager** | Hermes 主系统的 Session 上下文可以通过 MCP 触发 File Manager 操作（需要 Hermes 主系统实现 MCP Server） |

### 2.4 ❌ 不合适/难以打通的

| 路径 | 说明 |
|------|------|
| **OpenHuman 本地账号 → SSO** | OpenHuman 设计为本地优先，数据不上云，强依赖本地 SQLite |
| **Hermes 主系统 平台账号 → SSO** | Hermes 主系统的身份来自 Discord/Telegram 等平台，不是用户自建账号，难以映射到统一用户体系 |
| **Claude Code API Key → SSO** | Claude Code 依赖第三方 API Key，无法与 SSO 账号体系关联 |

### 3.2 数据流边界：raw/ vs compiled/

LLM Wiki 的目录结构体现了编译层与分发层的边界：

```
LLM Wiki wiki/
├── raw/                    ← 编译层（个人）
│   ├── inbox/             # 原始摄入内容
│   ├── notes/             # 个人笔记
│   └── attachments/       # 附件
│
├── compiled/              ← 分发层（企业）
│   ├── team_{team_id_1}/ # 团队隔离
│   │   ├── summary/      # LLM 摘要
│   │   ├── index/       # 向量索引
│   │   └── outputs/     # 编译产物
│   └── team_{team_id_2}/
│
└── wiki/                  ← 编译后的知识页面（双链）
```

**边界原则**：
- `raw/`（原始笔记）属于编译层，**不与企业 SSO/RBAC 打通**
- `compiled/`（编译产物）进入分发层，**通过 File Manager 的 Space 存储**
- 用户通过 Claudian 在 `raw/` 创作，编译后同步到 `compiled/`

### 3.4 各系统的正确使用模式

#### OpenHuman — 个人数据收集（不经过 SSO）

```
用途：个人 AI 助手，auto-fetch 邮件/日历/GitHub
认证：本地独立账号
数据：存在本地 SQLite，不上传云端
与团队交互：
  → 通过 MCP 写入 File Manager 空间（单向）
  → 无法通过 SSO 获取团队权限
```

#### Hermes 主系统 — 消息中枢（需改造后接入 SSO）

```
用途：多平台消息聚合路由
认证：平台 Pairing（现状）
问题：Discord/Telegram 用户 ≠ SSO 用户
改造方向：
  → 让 Hermes 主系统实现 MCP Server
  → Claude Code 通过 MCP 调用 Hermes
  → 但账号体系保持独立（平台绑定）
```

#### Hermes File Manager — 团队协作核心（SSO + RBAC）

```
用途：文件管理、空间权限、团队配额、审批流程
认证：JWT + SSO（已有）
角色：团队协作层的数据总线
对 LLM Wiki：
  → 同步文件到 LLM Wiki 时带上 team_id + user_id
  → LLM Wiki 按 team_id 隔离存储
  → RBAC 决定谁能触发同步、谁能编辑
```

#### LLM Wiki — 知识编译引擎（SSO + RBAC）

```
用途：知识 Ingest/Compile/Query/Lint
认证：信任 File Manager 传入的 JWT（改造后）
角色：被 File Manager 调用，自身不做权限判断
团队 wiki 隔离：
  wiki/
    team_{team_id_1}/
      raw/
      wiki/
      outputs/
    team_{team_id_2}/
      ...
```

#### Obsidian + Claudian — 知识浏览与编辑（通过 MCP 接入）

```
用途：可视化浏览 wiki，知识编辑，AI 辅助操作
认证：通过 MCP 调用 File Manager，RBAC 权限生效
与各系统交互：
  → 读取 LLM Wiki wiki/ 目录作为 Vault
  → Claude Code 执行 /ingest /query /lint
  → MCP 写入 File Manager 空间
```

#### Claude Code — 工具调用层（API Key，无 SSO）

```
用途：执行复杂任务、操作文件、调用 MCP 工具
认证：依赖各系统的 API Key 或 MCP
不经过 SSO，但受各系统的权限控制：
  → MCP 调用 File Manager → 受 RBAC 限制
  → MCP 调用 Hermes 主系统 → 受平台权限限制
```

## 四、知识工作流：/ingest /query /lint 的使用

### 4.1 Karpathy 的比喻

```
Obsidian = IDE（编辑器/界面）
LLM = 程序员（执行者）
Wiki = 代码库（操作对象）
```

### 4.2 在整合方案中的使用位置

| 命令 | 在哪里用 | 执行者 | 操作对象 |
|------|---------|--------|---------|
| **/ingest** | Claudian 对话框 | Claude Code | LLM Wiki wiki/（raw → wiki 编译） |
| **/query** | Claudian 对话框 | Claude Code | LLM Wiki wiki/（基于已编译知识回答） |
| **/lint** | Claudian 对话框或定时任务 | Claude Code | LLM Wiki wiki/（健康检查） |
| **/compile** | Claudian 对话框 | Claude Code | LLM Wiki raw/ → compiled/ |

**重要**：所有命令应在 **Claudian 侧边栏** 输入执行，**不是终端命令行**。

### 4.3 个人创作流程（编译层）

```
1. 用户在 Obsidian 编写笔记
       ↓
2. Claudian 侧边栏输入 /ingest "新的产品需求文档"
       ↓
3. Claude Code 执行 → 写入 LLM Wiki raw/
       ↓
4. Claudian 侧边栏输入 /compile "本周笔记"
       ↓
5. Claude Code 执行 → 生成摘要到 compiled/
       ↓
6. （可选）Hermes Auto-Fetch 补充内容到 Memory Tree
```

```bash
# Claudian 侧边栏正确用法
/ingest "新的产品需求文档"    # 摄入到 LLM Wiki raw/
/query "项目架构是什么"       # 搜索知识库
/lint                       # 健康检查
/compile "本周笔记"           # 编译摘要
```

### 4.4 团队分发流程（分发层）

```
1. 用户在 Obsidian 完成个人笔记编译
       ↓
2. Claude Code 同步到 Hermes File Manager 的个人 Space
       ↓
3. Hermes File Manager 触发 sync webhook
       ↓
4. LLM Wiki 处理变更 → 更新 compiled/ 和 index/
       ↓
5. 团队成员通过 LLM Wiki Query API 搜索知识
       ↓
6. 团队成员通过 Hermes File Manager 同步到本地 Obsidian
```

### 4.5 SSO 企业管理员流程

```
1. Admin 登录 Hermes File Manager
       ↓
2. 通过企业微信/飞书 SSO 登录（OAuth）
       ↓
3. Auth Service 验证 → 签发 JWT
       ↓
4. Admin 在 FM 后台管理团队成员和 Space 权限
       ↓
5. （自动）OrgSync 同步企业组织架构到 Team/Member
       ↓
6. 普通成员 SSO 登录 → 自动加入对应 Team
```

### 4.6 旧版工作流示意（参考）

```
用户（Claudian 输入）
       ↓
"请把这份资料摄入到知识库：raw/inbox/deepseek-v4.pdf"
       ↓

       ↓
```

## 五、整合方案总结

| 系统 | SSO/RBAC | 正确角色 | 不能做的事 |
|------|----------|---------|-----------|
| **OpenHuman** | ❌ | 个人 AI 助手，数据不上云 | 无法作为团队协作入口 |
| **Hermes 主系统** | ⚠️ | 消息路由中枢 | 难以对接团队 RBAC |
| **Hermes File Manager** | ✅ | 团队协作核心、数据总线 | 无（完整支持） |
| **LLM Wiki** | ✅ | 知识编译引擎 | 无法独立鉴权（依赖调用方） |
| **hermes-mcp** | ✅ | MCP Server 桥接层 | 打通 Claudian 与 FM/LLM Wiki |
| **Obsidian + Claudian** | ⚠️ | 知识浏览/编辑入口 | 通过 MCP 接入后才能团队协作 |
| **Claude Code** | ❌ | 工具执行层 | 不做权限判断，受各系统控制 |

```
│   ──────────────────              ───────────────────                        │
│                                                                              │
│   raw/（原始笔记）←── Claudian    compiled/（编译产物）←── LLM Wiki            │
│       ↓                              ↓                                      │
│   Hermes Memory Tree             Hermes File Manager                          │
│       ↓                              ↓                                      │
│   OpenHuman（本地）               TeamSpace（RBAC管控）                        │
│                                                                              │
│   ┌─────────────────────────────────┐                                        │
│   │  SSO/RBAC 打通边界               │                                        │
│   │  ─────────────────────          │                                        │
│   │  Hermes FM ←── JWT ──→ LLM Wiki │  ✅                                    │
│   │  Hermes ←──────────────→ FM     │  ❌（个人/企业隔离）                     │
│   │  OpenHuman ←──────────→ FM     │  ❌（本地/企业隔离）                     │
│   └─────────────────────────────────┘                                        │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 SSO 打通总结

| 功能 | Hermes File Manager | LLM Wiki | 打通方式 |
|------|---------------------|----------|----------|
| 登录认证 | ✅ | ✅ | 统一 JWT，由 FM 的 Auth Service 签发 |
| 团队成员 | ✅ | ✅ | JWT 中 teams 列表，Wiki 解析 |
| Space 权限 | ✅ | ✅ | Wiki 验证 user 属于 target team |
| 配额管理 | ✅ | ❌ | Wiki 无配额概念，只读 |
| 审批流 | ✅ | ❌ | Wiki 不参与审批 |

## 六、核心结论

1. **Hermes File Manager 是团队协作的唯一可信入口**（SSO + RBAC）
2. **LLM Wiki 通过 File Manager 调用，权限跟随 File Manager**
3. **OpenHuman 是个人工具，数据通过 MCP 单向流入 File Manager**
4. **Hermes 主系统需改造才能接入 SSO，否则保持独立**
5. **Claude Code 是执行工具，通过 MCP 受各系统权限控制**
6. **编译层（raw/）与分发层（compiled/）严格分离，SSO 不穿透编译层**
7. **SSO 用户默认 limited_access，通过 OrgSync 或 Admin 手动分配获得权限**
8. **hermes-mcp 是 Claudian 与 Hermes/LLM Wiki 打通的关键组件，实现 STDIO 模式的 MCP Server**

### 8.8 补充：SyncService 触发 LLM Wiki 处理

#### 背景

原文档规划中，SyncService 的 `record_sync()` 方法仅创建 SyncCursor 对象，**无回调机制**。同步完成后不会自动触发 LLM Wiki 的知识编译处理。

#### 实现方案

在 `services/sync_service.py` 中新增 `SyncWebhookCaller` 类，在 `record_sync()` 完成后自动调用 LLM Wiki 的 webhook 端点：

```python
        self._webhook_url = webhook_url

            return False

```

#### 与 hermes-mcp 的关系

| 组件 | 触发方式 | 用途 |
|------|---------|------|
| **SyncWebhookCaller** | 自动（同步后） | File Manager → LLM Wiki 自动同步 |
| **hermes-mcp sync_to_wiki** | 手动（MCP 调用） | Claudian 用户手动触发同步到 Wiki |

### 8.9 安全使用指南

#### 通用安全原则

| 原则 | 说明 | 在本系统中的应用 |
|------|------|----------------|
| **最小权限原则** | 默认只给最低限度的权限，按需逐步开放 | 新用户默认 limited_access；Claude Code 通过 MCP 调用时使用 viewer 角色 |
