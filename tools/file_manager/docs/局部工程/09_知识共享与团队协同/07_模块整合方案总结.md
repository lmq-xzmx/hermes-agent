## 二、能通过 SSO/RBAC 打通的部分

### 2.1 ✅ 可以打通的

| 路径 | 说明 |
|------|------|
| **File Manager → LLM Wiki** | File Manager 的 JWT 验证传入 team_id + user_id，LLM Wiki 按团队隔离 wiki 存储 |
| **Claudian MCP → File Manager** | 通过 MCP 调用 File Manager API，JWT 验证，RBAC 权限生效 |
| **Claude Code → File Manager** | 同上，通过 MCP 或 API |
| **Web UI → File Manager → LLM Wiki** | 用户在 File Manager Web 中触发知识同步，权限跟随账号 |
| **hermes-mcp → File Manager** | STDIO 模式 MCP Server，JWT Token 随请求传入，RBAC 权限生效 |
| **hermes-mcp → LLM Wiki** | 通过 File Manager 代理访问，team_id 隔离编译产物 |

### 2.2 SSO 打通实现细节：Hermes File Manager ↔ LLM Wiki

#### JWT Token 结构

File Manager 的 Auth Service 签发统一 JWT，LLM Wiki 验证后获取用户上下文：

```json
{
  "sub": "user_uuid",
  "username": "alice",
  "email": "alice@example.com",
  "teams": ["team_hermes", "team_research"],
  "roles": {"team_hermes": "admin", "team_research": "viewer"},
  "exp": 1700000000,
  "iat": 1699996400,
  "type": "access",
  "jti": "token_uuid"
}
```

#### LLM Wiki 认证中间件

```python
class HermesAuthMiddleware:
    """从 Hermes File Manager 传递的 JWT 验证"""

    def verify_token(self, token: str) -> UserContext:
        try:
            payload = jwt.decode(
                token,
                JWT_SECRET,
                algorithms=["HS256"]
            )
            return UserContext(
                user_id=payload["sub"],
                username=payload["username"],
                teams=payload.get("teams", []),
                roles=payload.get("roles", {}),
            )
        except jwt.ExpiredSignatureError:
            raise AuthError("Token 已过期，请重新登录")
```

#### SSO 用户权限状态流转

```
┌─────────────────────────────────────────────────────────────────┐
│                    SSO 用户权限状态流转                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   SSO 登录 ──→ 检查 Team 成员 ──→ 有成员记录 ──→ 正常访问    │
│       │                                    │                      │

│       │                                    ↓                      │
```

**SSO 用户首次登录时的权限状态**：
- 默认状态：`limited_access`（可登录，无法访问任何 Team/Space）
- 触发权限获取：Admin 分配 或 自动同步组织架构

### 2.3 ⚠️ 部分可以打通

| 路径 | 说明 |
|------|------|
| **OpenHuman → File Manager** | OpenHuman 的 auto-fetch 数据可以通过 MCP/API 写入 File Manager 空间（需 OpenHuman 支持 MCP 客户端模式） |
| **Hermes 主系统 → File Manager** | Hermes 主系统的 Session 上下文可以通过 MCP 触发 File Manager 操作（需要 Hermes 主系统实现 MCP Server） |

### 2.4 ❌ 不合适/难以打通的

| 路径 | 说明 |
|------|------|
| **OpenHuman 本地账号 → SSO** | OpenHuman 设计为本地优先，数据不上云，强依赖本地 SQLite |
| **Hermes 主系统 平台账号 → SSO** | Hermes 主系统的身份来自 Discord/Telegram 等平台，不是用户自建账号，难以映射到统一用户体系 |
| **Claude Code API Key → SSO** | Claude Code 依赖第三方 API Key，无法与 SSO 账号体系关联 |

### 3.2 数据流边界：raw/ vs compiled/

LLM Wiki 的目录结构体现了编译层与分发层的边界：

```
LLM Wiki wiki/
├── raw/                    ← 编译层（个人）
│   ├── inbox/             # 原始摄入内容
│   ├── notes/             # 个人笔记
│   └── attachments/       # 附件
│
├── compiled/              ← 分发层（企业）
│   ├── team_{team_id_1}/ # 团队隔离
│   │   ├── summary/      # LLM 摘要
│   │   ├── index/       # 向量索引
│   │   └── outputs/     # 编译产物
│   └── team_{team_id_2}/
│
└── wiki/                  ← 编译后的知识页面（双链）
```

**边界原则**：
- `raw/`（原始笔记）属于编译层，**不与企业 SSO/RBAC 打通**
- `compiled/`（编译产物）进入分发层，**通过 File Manager 的 Space 存储**
- 用户通过 Claudian 在 `raw/` 创作，编译后同步到 `compiled/`

### 3.4 各系统的正确使用模式

#### OpenHuman — 个人数据收集（不经过 SSO）

```
用途：个人 AI 助手，auto-fetch 邮件/日历/GitHub
认证：本地独立账号
数据：存在本地 SQLite，不上传云端
与团队交互：
  → 通过 MCP 写入 File Manager 空间（单向）
  → 无法通过 SSO 获取团队权限
```

#### Hermes 主系统 — 消息中枢（需改造后接入 SSO）

```
用途：多平台消息聚合路由
认证：平台 Pairing（现状）
问题：Discord/Telegram 用户 ≠ SSO 用户
改造方向：
  → 让 Hermes 主系统实现 MCP Server
  → Claude Code 通过 MCP 调用 Hermes
  → 但账号体系保持独立（平台绑定）
```

#### Hermes File Manager — 团队协作核心（SSO + RBAC）

```
用途：文件管理、空间权限、团队配额、审批流程
认证：JWT + SSO（已有）
角色：团队协作层的数据总线
对 LLM Wiki：
  → 同步文件到 LLM Wiki 时带上 team_id + user_id
  → LLM Wiki 按 team_id 隔离存储
  → RBAC 决定谁能触发同步、谁能编辑
```

#### LLM Wiki — 知识编译引擎（SSO + RBAC）

```
用途：知识 Ingest/Compile/Query/Lint
认证：信任 File Manager 传入的 JWT（改造后）
角色：被 File Manager 调用，自身不做权限判断
团队 wiki 隔离：
  wiki/
    team_{team_id_1}/
      raw/
      wiki/
      outputs/
    team_{team_id_2}/
      ...
```

#### Obsidian + Claudian — 知识浏览与编辑（通过 MCP 接入）

```
用途：可视化浏览 wiki，知识编辑，AI 辅助操作
认证：通过 MCP 调用 File Manager，RBAC 权限生效
与各系统交互：
  → 读取 LLM Wiki wiki/ 目录作为 Vault
  → Claude Code 执行 /ingest /query /lint
  → MCP 写入 File Manager 空间
```

#### Claude Code — 工具调用层（API Key，无 SSO）

```
用途：执行复杂任务、操作文件、调用 MCP 工具
认证：依赖各系统的 API Key 或 MCP
不经过 SSO，但受各系统的权限控制：
  → MCP 调用 File Manager → 受 RBAC 限制
  → MCP 调用 Hermes 主系统 → 受平台权限限制
```

##### Claude Code 运行模式分级

| 模式 | 适用角色 | 风险 | 说明 |
|------|---------|------|------|
| **YOLO 模式** | ⚠️ admin 推荐 | 高 | 直接执行，危险操作（如删除文件、强制覆盖） |
| **Safe 模式** | ✅ 所有角色推荐 | 低 | 推荐日常使用，稳健操作 |
| **Plan 模式** | ✅ 所有角色 | 无 | 先展示执行计划，确认后再执行 |

**隐喻**：
- **老板** ：庄园主可以随时叫学徒来演示工具（Plan/Safe），但自己不操作（不做 YOLO）
- **超级管理员** ：大管家给所有学徒分配工具箱，决定谁可以用什么工具
- **同事** ：可以自己用工具干活，但危险工具（YOLO）需要楼长批准
- **合作伙伴** ：只能看学徒演示（Plan），不能碰工具
- **普通用户** ：不知道有学徒这个角色

### 4.7 选择性共享 vs 完全共享模式

#### 两种模式对比

```
├── concepts（概念）：抽象知识结构
└── 图谱完整性（所有实体间的关联）

🔒 不共享的（即使完全信任）
├── 密码/密钥/令牌等明文敏感信息（系统自动检测并警告）
```

### 4.10 增量同步机制

#### 完全共享后的维护

完全共享后，客户的笔记修改不会每次都全量同步，而是增量同步：

| 变更类型 | 同步方式 |
|---------|---------|
| 新建笔记 | 立即同步 |
| 修改笔记 | 同步差异（只发送变更内容） |
| 删除笔记 | 同步删除（通知 Hermes 删除） |
| 修改标签 | 同步标签变更 |
| 新增链接 | 同步新链接关系 |
| 批量操作 | 合并后同步 |

#### 增量同步数据包示例

```json
{
  "type": "update",
  "path": "docs/microservice-arch.md",
  "diff": {
    "content_changed": true,
    "content": "# 微服务架构设计（v2）...",
    "tags": ["tech", "architecture", "microservices", "v2"],
    "links": ["项目Alpha", "GraphQL", "Kubernetes"]
  }
}
```

#### 安全机制：敏感内容扫描

> 扫描引擎在 Obsidian 中运行时，所有文件内容在本地内存中处理，敏感信息不会离开客户电脑。

```
数据流：

本地文件系统 → Claudian 插件 → [敏感扫描] → → 确认安全
                               ↕               ↕
                           发现风险          跳过/删除
                               ↕               ↕
                          弹窗提示客户      → 继续同步
```

**扫描规则**：
- 密码模式: `/password["']?\s*[:=]\s*["'].+["']/`
- API 密钥: `/sk-[A-Za-z0-9]{20,}/`
- AWS 密钥: `/AKIA[0-9A-Z]{16}/`
- 信用卡号: `/\b(?:\d{4}[- ]?){3}\d{4}\b/`
- 内部标记: `/机密|绝密|仅内部|confidential/i`

#### 增量更新的幂等性

- 同一内容重复发送 → 不会产生重复数据（通过 path + checksum 去重）
- 网络中断后重试 → 从断点继续（不重复传输已完成的部分）
- 冲突处理 → 以最新时间戳为准（客户本地的最后修改时间）

### 4.11 撤销与撤回机制

| 操作 | 命令 | 说明 |
|------|------|------|
| **一键撤销完全共享** | `@hermes undo-complete-share` | 撤销整个知识库的共享状态，团队内容标记为"来自客户，已撤回" |
| **逐篇撤回** | `@hermes unsync docs/microservice-arch.md` | 从团队 Space 中删除指定笔记 |
| **查看审计日志** | `@hermes audit-log` | 显示所有已同步的文件及访问记录 |
| **设置过期时间** | `@hermes set-expiry --date 2026-12-31` | 到期后自动撤销共享 |
| **暂停同步** | `@hermes pause-sync` | 临时暂停，恢复后自动同步期间的所有变更 |

## 六、核心结论

1. **Hermes File Manager 是团队协作的唯一可信入口**（SSO + RBAC）
2. **LLM Wiki 通过 File Manager 调用，权限跟随 File Manager**
3. **OpenHuman 是个人工具，数据通过 MCP 单向流入 File Manager**
4. **Hermes 主系统需改造才能接入 SSO，否则保持独立**
5. **Claude Code 是执行工具，通过 MCP 受各系统权限控制**
6. **编译层（raw/）与分发层（compiled/）严格分离，SSO 不穿透编译层**
7. **SSO 用户默认 limited_access，通过 OrgSync 或 Admin 手动分配获得权限**
8. **hermes-mcp 是 Claudian 与 Hermes/LLM Wiki 打通的关键组件，实现 STDIO 模式的 MCP Server**
9. **Claude Code 运行模式分级：YOLO（危险/admin推荐）、Safe（日常）、Plan（确认后执行）**

#### 与 hermes-mcp 的关系

#### 8.9.1 raw/ 个人笔记（超级管理员访问）

**背景**：raw/ 目录 = 用户的私人书房（个人知识笔记），本地优先、高隐私性、默认不共享。

| 操作 | 是否可行 | 场景 | 方法 |
| --- | --- | --- | --- |
| **技术故障排查** | ✅ 临时 | 用户反馈笔记丢失/损坏 | 仅查看用户授权的项目，最小覆盖 |
| **数据迁移** | ✅ 用户授权 | 用户从本地上传到团队知识库 | 需用户当面/邮件授权 + 双人操作 |
| **安全审计** | ✅ 合规需要 | 内部调查/数据泄露溯源 | 需法务或老板批准，生成只读访问日志 |
| **日常查看** | ❌ 禁止 | 无 | 系统不会触达 |
| **编辑/删除** | ❌ 禁止 | 无 | 不做任何写操作 |

**安全约束**：
```yaml
constraints:
  - 双人审核: "至少 2 人审批（用户本人 + 技术主管/安全官）"
  - 临时凭证: "仅 1 小时有效，scope 精确到具体用户"
  - 只读访问: "不可编辑、删除、下载"
  - 全栈日志: "操作过程录制 + 日志不可篡改"
  - 事后审计: "定期抽查超级管理员的 raw/ 访问记录"
```

### 9.5 Claudian + hermes-mcp = 工具入口

| 安全措施 | 状态 | 说明 |
|---------|------|------|
| **MCP 工具显式声明** | ✅ 已实现 | list_spaces、sync_to_wiki 等 |
| **RBAC 权限生效** | ✅ 已实现 | 通过 FM API 调用时验证 |

### 9.6 一句话安全选择

| 如果你想要... | 选择 | 安全重点 |
|-------------|------|---------|
| **本地存储、懂你的私人助手** | OpenHuman | 控制 auto-fetch 范围 |
| **团队协作、知识管理** | FM + LLM Wiki | JWT + RBAC + 审计 |
| **AI 执行工具、文件操作** | Claudian + hermes-mcp | MCP 白名单、命令审批 |

### 11.2 风险详情与修复建议

#### 🔑 风险一：JWT Secret 轮换机制缺失

| 项目 | 说明 |
|------|------|
| **风险等级** | 🔴 高 |
| **现状** | JWT secret 固定，长期有效 |
| **后果** | secret 泄露后，攻击者可伪造任意用户 Token |
| **修复建议** | Phase 0 实现 secret 自动轮换（90 天轮换 + 平滑切换） |

```
修复方案（庄园隐喻）：
🗝️ 管家每 90 天换一把新钥匙
🗝️ 旧钥匙还能用 7 天（平滑切换）
🗝️ 换锁记录写入审计日志（不可篡改）
```

#### 🔓 风险二：raw/ 访问的双人审批流程未实现

| 项目 | 说明 |
|------|------|
| **风险等级** | 🟡 中 |
| **现状** | 超级管理员理论上可访问任意用户的 raw/ |
| **后果** | 个人隐私（如个人笔记、实验草稿）可能被查看 |
| **修复建议** | Phase 3 前落地双人审批 + 临时 Token 技术方案 |

```
修复方案（庄园隐喻）：
🏠 大管家想进入住客的私人书房？
   ① 必须住客本人同意（开门）
   ② 必须技术主管批准（监督）
   ③ 全程录屏录像（审计）
   ④ 1 小时后钥匙自动失效（临时 Token）
   ⑤ 只能看，不能动任何东西（只读）
```

#### ⚒️ 风险三：Claude Code YOLO 模式风险

| 项目 | 说明 |
|------|------|
| **风险等级** | 🔴 高 |
| **现状** | YOLO 模式可直接执行任意命令，无确认 |
| **后果** | 误删文件、配置破坏、系统故障 |
| **修复建议** | Phase 3 前实现命令审批 + 容器隔离 |

```
修复方案（庄园隐喻）：
⚒️ 学徒想用锋利的刻刀（YOLO 模式）？
   ① 先给楼长展示雕刻方案（Plan 模式）
   ② 楼长审批后才允许动手（Safe 模式 + 确认）
   ③ 配备防护手套和护目镜（容器隔离）
   ④ 危险操作自动暂停（超时机制）
   ⑤ 事后检查工作成果（审计日志）
```

#### 🌐 风险四：跨团队编译"默认不可见"缺乏技术支撑

| 项目 | 说明 |
|------|------|
| **风险等级** | 🟡 中 |
| **现状** | 跨团队编译权限依赖人工管控，无 ACL 技术 |
| **后果** | 编译结果被未授权人员访问 |
| **修复建议** | LLM Wiki 实现 ACL，支持精确的团队/成员级别访问控制 |

```
修复方案（庄园隐喻）：
🌐 管家想把多楼层资料合并成报告？
   ① 报告默认锁在管家的保险柜（仅创建者+老板可见）
   ② 管家需明确指定谁能看（权限标记）
   ③ 报告过期自动销毁（TTL）
   ④ 外发文档自动加水印（合规水印）
   ⑤ 可随时撤销分享权限（撤销机制）
```
