# 自顶向下开发模式方法论

> **版本**: 1.0
> **更新日期**: 2026-05-02
> **适用项目**: Hermes File Manager

---

## 1. 核心理念

自顶向下开发是一种从抽象到具体、从整体到局部的系统化开发方法。其核心思想是：

1. **先全局后局部** - 先理解系统全貌，再分解实现
2. **先接口后实现** - 先定义契约，再编写代码
3. **先稳定后变化** - 先搭建稳定框架，再迭代功能

---

## 2. 分层架构

### 2.1 三层架构模型

```
┌─────────────────────────────────────────┐
│           Presentation Layer            │
│  (Vue Components, UI/UX, User Events)   │
├─────────────────────────────────────────┤
│             Domain Layer                 │
│  (Business Logic, Services, Engines)   │
├─────────────────────────────────────────┤
│          Infrastructure Layer            │
│    (Database, API, File System)        │
└─────────────────────────────────────────┘
```

### 2.2 每层职责

| 层级 | 职责 | 典型文件 |
|------|------|---------|
| Presentation | 用户交互、数据展示、事件收集 | `*.vue`, `*.js` |
| Domain | 业务规则、流程编排、状态管理 | `*Service.py`, `*Engine.py` |
| Infrastructure | 数据持久化、外部通信 | `server.py`, `models.py` |

### 2.3 依赖规则

- **上层可依赖下层**：Presentation → Domain → Infrastructure
- **下层不可依赖上层**：Infrastructure 不能 import Domain 的业务逻辑
- **同层可相互依赖**：Domain 内部 Service 之间可互相调用

## 3. 开发流程

### 3.1 需求转化步骤

```
┌──────────────────┐
│   业务需求分析     │  ← 产品需求文档
└────────┬─────────┘
         ↓
┌──────────────────┐
│   系统架构设计     │  ← SYSTEM_ARCHITECTURE.md
└────────┬─────────┘
         ↓
┌──────────────────┐
│   模块接口定义     │  ← API 契约、接口协议
└────────┬─────────┘
         ↓
┌──────────────────┐
│   增量式实现      │  ← 按依赖顺序实现
└────────┬─────────┘
         ↓
┌──────────────────┐
│   集成测试验证     │  ← 端到端测试
└──────────────────┘
```

### 3.2 接口先行原则 (Contract-First)

**步骤 1**: 定义接口协议（API Schema、事件契约）
**步骤 2**: 编写 Mock 实现或桩代码
**步骤 3**: 前后端并行开发
**步骤 4**: 集成联调验证

**示例**：

```yaml
# lifecycle_config.yaml - 约束规则契约
rules:
  - code: QUOTA_EXCEEDED
    message: "存储配额已用完"
    action: BLOCK
  - code: POOL_TEAMS_MIGRATING
    message: "团队正在迁移中"
    action: BLOCK
```

### 3.3 增量式实现

根据依赖关系确定实现顺序：

1. **无依赖** → 最先实现（基础设施）
2. **被依赖** → 次先实现（核心引擎）
3. **依赖他人** → 最后实现（UI 组件）

## 4. 任务分解方法

### 4.1 SMART 原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **S**pecific | 具体明确 | "实现文件上传引导" 而非 "完善引导系统" |
| **M**easurable | 可衡量 | "WebSocket 连接成功率 > 95%" |
| **A**chievable | 可实现 | 评估技术难度和工时 |
| **R**elevant | 相关性 | 与架构目标一致 |
| **T**ime-bound | 有时限 | "4小时内完成" |

### 4.2 任务分解粒度

- **大型任务** (>8h): 拆分为多个子任务
- **中型任务** (4-8h): 保持原样，明确验收标准
- **小型任务** (<4h): 可并行列为同一模块的工作项

### 4.3 依赖驱动排序

```
任务优先级 = f(被依赖数, 关键路径长度, 实现难度)

实现顺序:
1. 被最多任务依赖的先做
2. 处于关键路径上的先做
3. 难度低、被依赖少的可后做
```

## 5. 测试策略

### 5.1 测试金字塔

```
              ┌───────────┐
              │    E2E    │  ← 少量端到端测试，覆盖核心流程
             ┌───────────┐┌───────────┐
             │ Integration│  │ Contract  │
            ┌───────────┐┌───────────┐┌───────────┐
            │   Unit     ││   Unit     ││   Unit     │
            └───────────┘└───────────┘└───────────┘
```

### 5.2 各层测试职责

| 测试类型 | 覆盖范围 | 工具 | 覆盖率目标 |
|---------|---------|------|-----------|
| 单元测试 | Domain 层业务逻辑 | pytest | >80% |
| 集成测试 | API 端点、数据存储 | pytest + requests | >60% |
| E2E 测试 | 核心用户流程 | Playwright | 关键路径 |
| 契约测试 | 前后端接口协议 | Pact/Schemathesis | 100% |

### 5.3 TDD 流程

```
┌────────┐    Red     ┌────────┐   Green   ┌────────┐  Refactor
│ Write  │ ─────────> │  Run   │ ────────> │  Make  │
│  Test  │    测试    │  Test  │   测试    │  Pass  │
└────────┘    失败    └────────┘   通过    └────────┘
```

**步骤**：
1. **Red**: 编写一个失败的测试
2. **Green**: 编写最少量代码让测试通过
3. **Refactor**: 重构代码，消除重复

### 5.4 测试用例设计原则

- **独立性**: 每个测试用例可独立运行
- **可重复**: 相同结果，不受外部环境影响
- **自文档化**: 测试名称描述测试意图
- **快速执行**: 单元测试 < 100ms

## 6. 团队协作方法

### 6.1 垂直切割 vs 水平切割

| 切割方式 | 描述 | 适用场景 |
|---------|------|---------|
| **垂直切割** | 按业务功能切割 | 小团队、功能独立 |
| **水平切割** | 按技术层级切割 | 大团队、并行开发 |

**推荐**: 垂直切割为主，水平切割为辅

```
垂直切割示例:
├── M1: Admin 控制台 (3人)
│   ├── 前端组件
│   ├── 后端服务
│   └── WebSocket
├── M2: 生命周期约束 (2人)
│   ├── 规则引擎
│   └── 前端拦截器
└── M3: 新手引导 (5人)
    ├── 引导组件
    ├── Tour 组件
    └── 触发系统
```

### 6.2 代码审查流程

```
┌──────────────┐
│   开发者     │ ──> 创建 PR
└──────────────┘
       ↓
┌──────────────┐
│   审查者     │ ──> Code Review
└──────────────┘
       ↓
   通过? ──否──> 反馈修改
       ↓ 是
┌──────────────┐
│   合并代码   │
└──────────────┘
```

**审查清单**:
- [ ] 代码符合架构规范
- [ ] 有对应的单元测试
- [ ] 无安全漏洞
- [ ] 文档已更新

### 6.3 进度同步机制

| 同步方式 | 频率 | 内容 |
|---------|------|------|
| 每日站会 | 每天 | 进度、阻塞、计划 |
| 里程碑检查 | 每模块完成 | 集成测试、验收 |
| 每日更新 | 随时 | 文档同步 |

## 7. 文档规范

### 7.1 文档层次

| 文档类型 | 受众 | 更新频率 | 示例 |
|---------|------|---------|------|
| 架构文档 | 全体开发 | 重大变更 | SYSTEM_ARCHITECTURE.md |
| 设计文档 | 模块负责人 | 模块开发时 | MODULE_*.md |
| 实现文档 | 开发人员 | 实现时 | README.md |
| API 文档 | 前后端 | 接口变更 | api/*.yaml |

### 7.2 架构决策记录 (ADR)

```markdown
# ADR-001: 采用 WebSocket 实现实时推送

## 状态: 已接受
## 日期: 2026-05-02

## 背景
Admin 控制台需要实时显示统计数据

## 决策
采用 WebSocket 替代轮询

## 后果
- 优点: 实时性高、服务器压力小
- 缺点: 需要维护长连接
```

## 8. 质量保障

### 8.1 代码质量指标

| 指标 | 目标值 | 测量工具 |
|------|--------|---------|
| 测试覆盖率 | >80% | pytest-cov |
| 代码重复率 | <5% | SonarQube |
| 圈复杂度 | <10 | ESLint |

### 8.2 持续集成

```
代码提交 → 静态分析 → 单元测试 → 集成测试 → 构建 → 部署
```

### 8.3 性能基准

| 指标 | 目标值 |
|------|--------|
| API 响应时间 | <200ms (p95) |
| 页面加载时间 | <3s |
| WebSocket 延迟 | <100ms |

## 9. 最佳实践清单

### 开发前
- [ ] 理解系统架构全貌
- [ ] 明确模块职责和边界
- [ ] 定义接口契约
- [ ] 评估任务依赖关系

### 开发中
- [ ] 遵循接口先行原则
- [ ] 增量实现，每步可运行
- [ ] 编写单元测试
- [ ] 保持代码简洁

### 开发后
- [ ] 通过 Code Review
- [ ] 更新相关文档
- [ ] 运行集成测试
- [ ] 验证性能指标
